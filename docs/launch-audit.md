## 4. 결제 체인 진단 (수정하지 않음)

현재 흐름: `accept_application()`(사용자 권한, 조건부 이중 UPDATE) → service role로 빌링키 조회 →
`tossGateway.chargeBilling` → 성공하면 `finalize_accepted_application()` / 실패하면
`revert_failed_acceptance()`.
DB 쪽 원자성(철회 레이스, 중복 낙찰 차단, NULL-safe 판매자 확인, service_role 전용 finalize/revert)은
§3 스펙대로 **잘 구현되어 있다.** 문제는 외부 호출 전후의 **보상 처리**에 몰려 있다.

| # | 위험 | 시나리오 | 심각도 |
|---|---|---|---|
| P1 | 결제는 됐는데 확정이 안 됨 | charge 성공 → `finalize`가 DB 오류·함수 타임아웃·프로세스 종료로 실패하면 **구매자 돈은 빠졌는데** 지원서는 `accepted`, 매물은 `awarded`로 남고 transaction은 없다. 환불도 없고 재시도 경로도 없다 | 높음 |
| P2 | charge 호출 예외 | `tossFetch`가 네트워크 오류나 JSON이 아닌 응답에서 **throw**하는데 route에 try/catch가 없다 → 500이 나고, revert가 안 되며, 매물이 `awarded`에 영구히 묶인다. 타임아웃이면 토스 쪽은 결제가 됐을 수도 있다(결과를 모름) | 높음 |
| P3 | revert 실패를 무시 | `revert_failed_acceptance` 반환 에러를 확인하지 않는다 | 중간 |
| P4 | 멱등성 없음 | `Idempotency-Key` 헤더를 쓰지 않는다. orderId=application.id라서 같은 주문 재시도는 토스가 막아주지만, 결과를 모를 때 `GET /v1/payments/orders/{orderId}`로 대조하는 로직이 없다 | 중간 |
| P5 | 카드 등록 대상을 위조할 수 있음 | `/pay/billing-auth?customerKey=<uuid>`의 customerKey가 로그인 사용자와 연결되어 있지 않다. `items.seller_id`가 공개 컬럼이라 다른 사람의 UUID를 알아낼 수 있고, 그 사람의 `billing_keys`를 **내 카드로 덮어쓸 수 있다**. `clientRedirect`도 검증 없이 리다이렉트한다(오픈 리다이렉트) | 중간(보안) |
| P6 | 수령시한 고정 | `pickup_deadline = now + 24h` 하드코딩 (등록 화면에 수령시한 UI가 없음) | 낮음 |
| P7 | 모바일 예외 처리 | `applicants.tsx`의 `handleAcceptConfirm`에 catch가 없다 → 네트워크 오류가 나면 알림 없이 조용히 실패한다. 서버는 성공했는데 응답만 유실되면, 다시 누를 때 "방금 철회됐어요"(TT409)라는 **틀린 문구**가 나온다 | 중간 |
| P8 | 409 문구가 하나뿐 | 매물이 이미 낙찰된 경우와 지원서가 철회된 경우 모두 "방금 철회됐어요"로 나온다 | 낮음 |
| P9 | 푸시 없음 | §3의 "낙찰자/탈락자/판매자 푸시"를 보내지 않는다 | Phase 4 |
| P10 | 함수 실행 시간 | Vercel에 배포하면 route에 `maxDuration`을 지정하지 않았다. 토스가 늦게 응답하면 P1/P2로 이어진다 | 중간 |

  둘 다 해외 법인이라 국외 이전 해당 여부가 실제로 모호하다 — 법률 검토 항목으로 남겨뒀다.
- ~~계정 삭제 기능이 아직 없는 상태로 정책 페이지가 배포된다~~ — **해결(2026-09-28)**: 3단계에서
  설정 화면·웹 요청 페이지를 실제로 만들었다. §8/제7조 문구를 실제 경로(거래 탭 > 설정,
  `/account/delete`)로 갱신했다.
- **카카오 키가 아직 플레이스홀더다(`placeholder_client_id`)** — `supabase/.env`의
  `SUPABASE_AUTH_EXTERNAL_KAKAO_CLIENT_ID` 실제 값을 카카오 로컬 API로 호출해 직접 확인했다
  (§1에서 "실 키 미설정"으로만 적었던 걸 이번에 재확인). 카카오 로그인뿐 아니라 이번에 추가한
  온보딩 동네 자동설정/검색(§6 onboarding.tsx)도 실 키 없이는 동작하지 않는다 — 코드 경로는
  401을 정상적으로 처리하는 것까지 확인했고(`scripts/verify-stage3.mjs`로 검증하지 않은 부분,
  수동 curl로 확인), 검색 실패 시 직접 입력 폴백을 넣어 온보딩 자체가 막히지는 않는다. 카카오
  개발자센터에서 앱 등록 + REST API 키 발급 + 로컬 API 사용 설정이 필요 — `docs/phone-check.md`에
  실기기 확인 항목으로 남긴다(6단계).
- **신고(reports) 처리 화면이 없다**: 신고는 DB에 쌓이기만 하고 운영자가 Supabase 대시보드에서
  직접 확인해야 한다(MVP 범위 — `docs/decisions.md` 3단계). 신고가 쌓이기 시작하면 최소한의
  조회 화면이나 payment_incidents처럼 Discord 알림을 검토할 것.
- **계정 삭제 웹 요청(`/account/delete`)은 즉시 처리가 아니다**: 웹 로그인이 없어 본인 확인 없이
  자동 삭제할 수 없다 — 요청을 `account_deletion_requests`에 적재하고 수동 처리한다. 요청이
  쌓이면 처리 절차(누가, 어떤 주기로)를 정해야 한다.
